핵심은 특정 코딩 스타일을 고집하는 것이 아니라 <b>재사용 빈도, 성능 영향, 변경 가능성, 가독성을 기준으로 구현 방식을 선택하는 것</b>입니다.

## 문제 해결 경험

### 잦은 기획 변경에 대응하기 위한 구현 기준 조정

- <b>상황:</b> 실무에서 하루에도 기획이 여러 차례 변경되어 기존처럼 모든 객체를 세분화해 선언하고 재활용하는 방식은 수정 속도와 탐색 비용 측면에서 비효율적일 수 있었습니다.
- <b>판단:</b> 성능상 의미 있는 재사용과 단순한 추상화를 구분하고, 변경 가능성이 높은 UI 로직에서는 코드만 보고도 대상과 동작을 빠르게 파악할 수 있는 것이 더 중요하다고 판단했습니다.
- <b>행동:</b> 팀원 코드 리뷰 및 교육 시 빠르고 직관적인 구현을 요청했습니다. 바인딩 객체 역시 반드시 별도 저장하는 방식 대신, 재사용 필요성이 낮은 경우 필요한 위치에서 직접 사용하도록 하여 UI 이름과 사용 위치를 쉽게 찾고 수정할 수 있도록 했습니다.
- <b>의미:</b> 최적화 자체를 목표로 하기보다 실제 프로젝트의 변경 빈도와 유지보수 비용까지 고려해 코드 작성 기준을 조정한 경험입니다.

<b>추가 보강 필요:</b> 이 방식 적용 전후의 수정 시간, 반복 작업 감소, 팀원 피드백 등 정량적 결과가 확보되면 사례를 강화할 수 있습니다.

### 대량 상품 이미지 로딩으로 인한 메모리 증가 및 강제 종료 해결

- <b>상황:</b> 기존 텍스처 관리 구조는 다운로드한 리소스를 캐시에 보관하고 재활용하는 방식이었습니다. 한정된 이미지 세트를 반복 사용하는 게임에서는 효율적일 수 있지만, 상품 이미지가 지속적으로 추가·로드되는 쇼핑 서비스에서는 다운로드된 텍스처가 계속 누적되는 문제가 발생했습니다.
- <b>분석:</b> 앱 사용 중 강제 종료 현상을 조사하면서 <b>Unity Profiler를 통해 메모리 사용량이 지속적으로 증가하는 것을 확인</b>했고, 기존 캐시 중심의 텍스처 생명주기가 서비스 특성과 맞지 않는 것이 원인이라고 판단했습니다.
- <b>개선:</b> 상품 이미지처럼 재사용 가능성이 낮은 동적 텍스처는 장기 캐시에 유지하지 않고, <b>화면의 개별 오브젝트와 텍스처의 생명주기를 연결</b>했습니다. 해당 오브젝트가 제거될 때 자신이 사용하는 텍스처도 함께 해제될 수 있도록 관리 방식을 변경했습니다.
- <b>2차 이슈:</b> 동일한 이미지 리소스를 두 UI 오브젝트가 공유하는 경우 한쪽 오브젝트가 파괴되면서 공유 텍스처까지 해제되어, 남아 있는 UI가 검은 이미지로 표시되는 문제가 발생했습니다.
- <b>해결:</b> 이미지 인스턴스를 구분할 수 있도록 <b>각 사용 단위에 고유 키를 부여하여 텍스처 소유권을 분리</b>했고, 한 오브젝트의 해제가 다른 오브젝트에 영향을 주지 않도록 수정했습니다.
- <b>결과:</b> 정확한 메모리 사용량 수치는 별도로 기록하지 못했지만, Profiler에서 확인되던 <b>텍스처 메모리의 중첩 누적 현상을 해소</b>했고, 수정 이후 해당 원인으로 발생하던 <b>앱 크래시가 더 이상 재현되지 않았습니다.</b>
- <b>의미:</b> 단순히 캐시를 제거한 것이 아니라 <b>게임과 쇼핑 서비스의 리소스 사용 패턴 차이를 파악하고, Profiler로 원인을 추적한 뒤 텍스처 생명주기와 소유권 모델을 서비스 특성에 맞게 재설계한 경험</b>입니다.
